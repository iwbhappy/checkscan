# ТЗ: мобильное приложение «CheckScan» (Flutter) — учёт трат по фискальным чекам Казахстана

## 0. Как работать с этим ТЗ (для Codex)

- Реализуй приложение целиком, по этапам из раздела 14. После каждого этапа проект должен собираться (`flutter analyze` без ошибок, `flutter test` зелёный).
- Если в ТЗ чего-то не хватает — выбирай самый простой вариант, фиксируй решение в `docs/DECISIONS.md`. Не останавливайся с вопросами.
- Единственный неизвестный кусок — точный формат ссылки в нижнем QR и HTML/JSON страницы ОФД (раздел 6). Делай его **заменяемым** через интерфейс и покрывай тестами с фикстурами. Не придумывай поля, которых не видел в реальном ответе: сначала сохрани реальный ответ в `test/fixtures/`.

## 1. Цель

Пользователь фотографирует (или выбирает из галереи / сканирует live-камерой) бумажный фискальный чек. Приложение само находит на чеке QR-код, по нему получает от ОФД структурированные данные чека (магазин, дата, позиции, суммы, НДС) и сохраняет их локально как траты. Затем пользователь видит историю, фильтры и статистику.

Основной сценарий: **навёл камеру на чек → через 1–3 секунды чек разобран и сохранён**.

## 2. Исходные данные: как выглядит чек

Пример (магазин Small, ТОО «Скиф Трейд», Павлодар, ОФД — АО «Казахтелеком»):

- Шапка: название юрлица, адрес.
- Служебные поля: фискальный признак/номер (`1462733895#308128`), ЗНМ (заводской номер) `502220466`, БИН/БСН `131141020408`, РНМ/МТН `0010102236118`, дата-время `07-10-2026 17:32` (**формат ДД-ММ-ГГГГ ЧЧ:ММ**), касса, смена, номер продажи, «Покупатель КСО».
- Позиции: `№ штрихкод Название (двуязычное: каз - рус - производитель)`, затем `ntin:...`, цена, `*кол-во`, `=сумма`.
- «ККС/НДС 16.0 % = 276.12», «ИТОГО К ОПЛАТЕ = 2002.00», «ИТОГО БЕЗ СКИДКИ = 2244.00», «ВСЕ СКИДКИ = 242.00». Заметь: сумма позиций (299+435+489+779=2002) уже равна итогу — скидка показана справочно.
- Внизу **два QR-кода и штрихкод**:
  1. Верхний QR под текстом «Получить 1000 тенге» — рекламный/регистрация на SMALL.KZ. **Игнорировать.**
  2. Штрихкод + строка `010.1452.071026.0122` — внутренний номер магазина. Не использовать.
  3. **Нижний QR (под строкой `010.1452.071026.0122`) — ссылка на данные чека в ОФД. Это основной источник данных.** Рядом подпись «ОФД: АО "Казахтелеком"».
- Чеки других магазинов/ОФД Казахстана (Kaspi, Magnum, Galmart, ОФД Транстелеком, Кофд и т.д.) могут иметь другую вёрстку, но QR на ссылку ОФД есть всегда.

## 3. Не-цели (в v1 не делаем)

- Бэкенд, аккаунты, облачная синхронизация, мультиустройство.
- OCR текста чека. Вся логика — через QR + ОФД. (OCR как резервный вариант — только в разделе «Будущее», 15.)
- Чеки не из Казахстана.
- iOS-специфичные фичи, публикация в сторах (но код должен собираться и под iOS без правок логики).

## 6. Получение данных чека из QR (самое важное)

### 6.1 Что известно (подтверждено реальным QR с чека-примера)
Нижний QR кодирует такую строку (в ней `&amp;` — это HTML-экранированный `&`; **перед разбором обязательно декодировать `&amp;` → `&`**):

```
http://consumer.oofd.kz?i=1462733895&amp;f=010102236118&amp;s=2002.00&amp;t=20261007T153259
```

Параметры (сопоставление с чеком):

| Параметр | Значение | Что это |
|---|---|---|
| `i` | `1462733895` | фискальный признак (на чеке: `1462733895#308128`) |
| `f` | `010102236118` | РНМ кассы (на чеке: `0010102236118` — на один ведущий ноль больше; сравнивать **без ведущих нулей**) |
| `s` | `2002.00` | итоговая сумма |
| `t` | `20261007T153259` | дата-время `ГГГГММДДTччммсс` |

Важные нюансы:
- **Схема `http`, не `https`.** Сначала пробовать `https://` с теми же параметрами, при ошибке — `http://`. Для Android включить cleartext только для хоста `consumer.oofd.kz` через `network_security_config.xml` (не `usesCleartextTraffic=true` для всего приложения).
- **Время `t` (15:32:59) не совпадает с печатным временем на чеке (17:32)** — разница 2 часа. Таймзону `t` не угадывать: установить по реальному ответу ОФД (какое время он показывает в самом чеке) и записать в `docs/OFD_FORMAT.md`. Для дедупликации и отображения использовать время из ответа ОФД; если его нет — `t` с выясненным смещением.
- Минимально по QR уже известны: фискальный признак, РНМ, сумма и время. Это нужно сохранить даже если загрузка позиций с ОФД не удалась (чек уходит в `pending` с этими данными, а в истории показывается сумма и время).
- Хост `consumer.oofd.kz` — первый и обязательный `OfdProvider`; `canHandle` = хост оканчивается на `oofd.kz` + есть параметры `i`, `f`, `s`, `t`.

**Формат ответа сайта (HTML/JSON) пока неизвестен — Codex должен установить его сам** по шагам ниже.

### 6.2 Обязательный шаг-исследование (до написания парсера)
1. Создай dev-скрипт/экран «Debug», который показывает **сырое содержимое QR-строки** и сохраняет его в лог.
2. Пользователь предоставит 2–5 реальных QR-строк (или фото чеков в `test/fixtures/photos/`). Возьми из них QR-строки и положи в `test/fixtures/qr_strings.txt`. Первая строка уже известна (чек из примера): `http://consumer.oofd.kz?i=1462733895&amp;f=010102236118&amp;s=2002.00&amp;t=20261007T153259`.
3. Для каждой строки выполни HTTP GET (dio, браузерный `User-Agent`, `Accept-Language: ru`, follow redirects) и **сохрани тело ответа** в `test/fixtures/ofd_responses/*.html|json`.
4. Определи, как отдаются данные:
   - **Вариант A**: страница — SPA, а данные приходят отдельным XHR/JSON-запросом → смотри в HTML/JS URL API, реализуй прямой вызов JSON-эндпоинта (предпочтительно).
   - **Вариант B**: данные есть прямо в HTML → парси `html`-пакетом по устойчивым селекторам.
   - **Вариант C**: нужен JS-рендер → fallback: скрытый `webview_flutter`, дождаться загрузки, достать DOM/JSON через `runJavaScriptReturningResult`.
5. Результат исследования запиши в `docs/OFD_FORMAT.md`: формат QR-URL, эндпоинты, структура ответа, пример.

### 6.3 Модель, в которую приводим любой ответ

```dart
class ParsedReceipt {
  String? ofdName;            // "АО Казахтелеком"
  String sellerName;          // ТОО "Скиф Трейд"
  String? sellerBin;          // 131141020408
  String? storeAddress;       // Павлодар, Ак. Сатбаев, 47
  String? kkmRegNumber;       // РНМ 0010102236118
  String? kkmSerial;          // ЗНМ 502220466
  String? fiscalSign;         // 1462733895
  String? receiptNumber;      // 122 / 308128
  DateTime dateTime;          // 2026-10-07 17:32 (локальное время Asia/Almaty, храним UTC+ исходное смещение)
  int totalMinor;             // 200200 (в тиынах, ИТОГО К ОПЛАТЕ)
  int? discountMinor;         // 24200
  int? vatMinor;              // 27612
  double? vatRate;            // 16.0
  String? paymentType;        // cash/card/mixed, если есть
  List<ParsedItem> items;
  String sourceUrl;           // исходная ссылка из QR
}
class ParsedItem {
  String name;                // русская часть названия, если двуязычное; полное — в rawName
  String rawName;
  String? barcode;            // 4607065001445
  String? ntin;               // 0200092089208
  double quantity;            // 1 или 0.534 (весовой)
  String? unit;               // шт / кг
  int unitPriceMinor;         // 29900
  int sumMinor;               // 29900
  int? discountMinor;
}
```

### 6.4 Правила
- **Все деньги хранить в целых тиынах (`int`)**, никогда `double`. Парсинг `"299.00"`, `"299,00"`, `"1 299.00"` → 29900.
- Валюта по умолчанию KZT (₸); поле `currency` в БД.
- Даты: на чеке `ДД-ММ-ГГГГ ЧЧ:ММ`; в ответе ОФД может быть ISO. Парсер принимает оба. Таймзона по умолчанию `Asia/Almaty` (UTC+5 с 2024).
- Двуязычные названия вида `Галицков сүті 1 л 2,5% финпак - Молоко галиц.1л 2,5% - ПАВЛОДАР МОЛОКО`: `rawName` — как есть; `name` — **русская часть** (эвристика: сегмент с преобладанием кириллицы без казахских букв `ә ғ қ ң ө ұ ү һ і`; если не удалось — rawName).
- **Валидация после парсинга**: `sum(items.sum) == total` (допуск ≤ 1 тиын на позицию; с учётом скидок). Если не сходится — сохранить чек с флагом `needsReview = true` и показать пользователю предупреждение, но не терять данные.
- Сетевые ошибки: таймаут 15 с, 2 повтора с backoff. Ошибки типизированы (раздел 11).
- Чек, который не удалось распознать/скачать, **не теряется**: сохраняется как «черновик» со ссылкой и статусом `pending`, с кнопкой «Повторить» и автоповтором при появлении сети.

### 6.5 Выбор нужного QR, если их несколько на изображении
`mobile_scanner` вернёт все коды. Алгоритм выбора:
1. Оставить только QR с содержимым-URL (`http/https`).
2. Сначала HTML-декодировать содержимое (`&amp;` → `&`). Если у кандидата `canHandle` вернул true в одном из OfdProvider → это он.
3. Исключить явно рекламные/регистрационные ссылки (хост содержит `small.kz`, `promo`, и т.п. — список хостов-исключений в конфиге).
4. Если остались несколько — взять тот, что расположен **ниже** на изображении (по bounding box из `Barcode.corners`).
5. Если ни одного — ошибка «QR чека не найден», совет сфотографировать ближе и ровнее.

## 7. Функциональные требования

### 7.1 Экран сканирования (главный)
- Live-камера с рамкой-видоискателем, автофокус, кнопка фонарика, подсказка «Наведите на нижний QR-код чека».
- Автоматическое распознавание: как только найден валидный QR чека → вибро-отклик, остановка камеры, запуск загрузки (индикатор «Получаем чек…»).
- Кнопка **«Из галереи»**: выбор фото (как в примере — длинный чек на фоне, фото под углом, с бликами). Использовать `analyzeImage`; если не нашлось — повторить на масштабированных/контрастных копиях (увеличить ×2, ×3, grayscale + порог) и на кропе нижней трети. Только после неудачи показать ошибку.
- Кнопка **«Вставить ссылку»** (ручной ввод/вставка URL из буфера обмена) — запасной путь.
- Защита от дублей: ключ из QR — `(fiscalSign=i, kkmRegNumber=f без ведущих нулей, sum=s)` (доступен сразу, до загрузки с ОФД; время `t` в ключ не включать из-за расхождения часовых поясов); при дубле — диалог «Этот чек уже добавлен» с переходом к нему.

### 7.2 Экран результата / редактирования чека
- Заголовок: магазин, адрес, дата-время, итого крупно.
- Таблица позиций: название, кол-во × цена, сумма, категория (чип, можно сменить).
- Редактирование: название магазина, дата, категория на уровне чека и позиции, удаление позиции, добавление позиции, заметка. При изменении позиций — пересчёт итога, флаг `edited`.
- Кнопки: «Сохранить», «Удалить», «Открыть в ОФД» (внешний браузер по `sourceUrl`).
- Чек сохраняется автоматически сразу после успешного парсинга; экран — это просмотр/правка уже сохранённого.

### 7.3 История
- Список чеков, сгруппированный по дням (сегодня/вчера/дата). Карточка: магазин, время, сумма, число позиций, бейдж «проверить», если `needsReview`.
- Поиск по магазину и названию позиций (полнотекстово через LIKE/FTS5).
- Фильтры: период (день/неделя/месяц/свой диапазон), магазин, категория, диапазон сумм.
- Свайп влево — удалить (с Undo через SnackBar).
- Pull-to-refresh перепробует `pending`-чеки.

### 7.4 Статистика
- Период: неделя / месяц / год / произвольный; навигация «← предыдущий / следующий →».
- Сводка: общая сумма, число чеков, средний чек, сравнение с прошлым периодом (± %).
- Круговая/кольцевая диаграмма по категориям, список категорий с суммой и долей.
- Столбчатая диаграмма по дням/неделям/месяцам.
- Топ-10 магазинов, топ-10 товаров по сумме и по частоте покупок.
- Тап по категории/магазину → история с применённым фильтром.

### 7.5 Категории
- Предустановленные: Продукты, Молочное, Мясо и рыба, Овощи и фрукты, Хлеб и выпечка, Сладости и снеки, Напитки, Алкоголь, Бытовая химия, Гигиена и уход, Аптека, Одежда, Электроника, Кафе и рестораны, Транспорт и топливо, Прочее. Название, цвет, иконка; пользователь может добавлять/править/удалять свои.
- **Автокатегоризация позиций**: правила «ключевое слово в названии → категория» (стартовый словарь в `assets/category_rules.json`, например: «молоко/сметана/творог/кефир/сыр» → Молочное; «snickers/шоколад/батончик/конфет» → Сладости и снеки; «пиво/водка/вино» → Алкоголь). Приоритет: пользовательское правило > встроенное > Прочее.
- Когда пользователь вручную меняет категорию позиции — предложить «Запомнить для всех «<название>»?» и сохранить правило (ключ — нормализованное название либо штрихкод; штрихкод точнее).
- Категория чека по умолчанию = категория с наибольшей суммой позиций.

### 7.6 Настройки
- Экспорт: CSV (чеки и позиции, UTF-8 с BOM для Excel, разделитель `;`) и JSON-бэкап через `share_plus`.
- Импорт JSON-бэкапа (слияние без дублей).
- Валюта и формат (по умолчанию ₸, `1 234,56 ₸`).
- Тема: светлая/тёмная/системная.
- «Удалить все данные» с двойным подтверждением.
- «О приложении», версия.

### 7.7 Приём чека извне (этап 7, опционально)
- Если пользователь «Поделился» фото или ссылкой в приложение (share-intent) — открыть и обработать тем же пайплайном.

## 8. База данных (Drift / SQLite)

```
stores        (id, name, bin UNIQUE NULLABLE, address)
categories    (id, name, color, icon, isBuiltIn, sortOrder)
receipts      (id, storeId→stores, ofdName, kkmRegNumber, kkmSerial, fiscalSign,
               receiptNumber, dateTimeUtc, tzOffsetMin, totalMinor, discountMinor,
               vatMinor, vatRate, currency, paymentType, sourceUrl, status
               [pending|ok|error], needsReview, edited, note, categoryId→categories,
               createdAt, updatedAt)
receipt_items (id, receiptId→receipts ON DELETE CASCADE, position, name, rawName,
               barcode, ntin, quantity REAL, unit, unitPriceMinor, sumMinor,
               discountMinor, categoryId→categories)
category_rules(id, kind [keyword|barcode], pattern, categoryId, isUser)
```

- Уникальный `dedupKey TEXT UNIQUE` = `"{fiscalSign}|{kkmRegNumber без ведущих нулей}|{totalMinor}"` — строится из полей QR (`i`, `f`, `s`), поэтому доступен ещё до загрузки данных с ОФД.
- Индексы: `receipts(dateTimeUtc)`, `receipt_items(receiptId)`, `receipt_items(categoryId)`, `receipt_items(barcode)`.
- Миграции через Drift `MigrationStrategy`, версия схемы с первого дня, тест миграций.
- Всё хранится только локально. Никакой телеметрии.

## 9. UI / UX

- Material 3, светлая и тёмная темы, seed-цвет зелёный/бирюзовый.
- Нижняя навигация: **Скан** (центральная крупная кнопка), **История**, **Статистика**, **Настройки**.

- Анимации сдержанные; успешное сканирование — галочка + вибро.

## 10. Нефункциональные требования

- Холодный старт до готовой камеры ≤ 2 с на среднем Android.
- Распознавание QR по live-камере ≤ 1 с при нормальном свете.
- Приложение полностью работает офлайн, кроме загрузки нового чека; без сети чек уходит в `pending`.
- Хранение данных — только на устройстве. Сетевые запросы — **только** к хосту из QR-ссылки и только для получения данных чека (проверять схему https и отсутствие редиректа на неожиданные хосты: whitelist доменов ОФД в конфиге, неизвестный домен — показать пользователю и спросить).
- Никаких секретов/ключей в репозитории.
- Покрытие тестами домена и парсеров ≥ 80%.

## 11. Обработка ошибок

Типизированные ошибки (`sealed class AppFailure`) и понятные русские сообщения:

| Ситуация | Сообщение / действие |
|---|---|
| Нет разрешения на камеру | Экран с объяснением и кнопкой «Открыть настройки» |
| QR не найден на фото | «Не нашли QR чека. Сфотографируйте нижний QR ближе и ровнее» |
| QR найден, но не ссылка ОФД | «Это не QR чека» + показать содержимое |
| Нет сети | Сохранить `pending`, «Загрузим, когда появится интернет» |
| Таймаут/5xx ОФД | Повтор ×2, затем `pending` с кнопкой «Повторить» |
| Чек не найден в ОФД (404/пусто) | «ОФД ещё не получил чек, попробуйте через несколько минут» → `pending` |
| Не удалось распарсить | `status=error`, сохранить сырой ответ в `debugRaw` (только debug-сборка), кнопка «Отправить разработчику» в debug |
| Сумма позиций ≠ итогу | сохранить, `needsReview=true`, предупреждение |
| Дубликат | Диалог с переходом к существующему чеку |

Данные чека ОФД может отдать с задержкой после покупки — это нормальная ситуация, учесть автоповтор `pending` (через 1, 5, 30 мин и при запуске приложения).

- **Unit**: парсер денег, парсер дат, выбор русской части названия, автокатегоризация, валидатор сумм, выбор QR из нескольких, дедупликация.
- **Parser tests**: на каждый файл из `test/fixtures/ofd_responses/` — ожидаемый `ParsedReceipt` в соседнем `*.expected.json`. Обязательный кейс — чек из примера: 4 позиции (299.00, 435.00, 489.00, 779.00), итого 2002.00, НДС 16% = 276.12, скидки 242.00, БИН 131141020408, РНМ 0010102236118, дата 2026-10-07 17:32, продавец ТОО «Скиф Трейд».

- **Widget**: список истории, экран чека (редактирование и пересчёт), состояния ошибок.
- **Integration (smoke)**: прогон «фото из `test/fixtures/photos/` → analyzeImage → mock Dio с фикстурой → чек в БД».

- Отдельный ручной чек-лист в `docs/MANUAL_QA.md`: блики, мятый чек, чек под углом, тусклый свет, крупный и мелкий QR, чек с 50+ позициями, весовые товары, чек возврата (если встретится).

## 13. Критерии приёмки (MVP)

1. На Android-устройстве/эмуляторе: навести камеру на реальный чек → в течение 3 с на экране разобранный чек с правильными позициями и суммой; запись есть в истории после перезапуска приложения.
2. Загрузка фото чека из галереи (как в примере: фото под углом на фоне с узором) находит нужный QR и игнорирует верхний рекламный.
3. Повторное сканирование того же чека не создаёт дубль.
4. В режиме полёта чек сохраняется как `pending` и автоматически догружается при появлении сети.
5. Статистика за месяц показывает суммы по категориям и дням, совпадающие с суммой чеков в истории.
6. Экспорт CSV открывается в Excel с корректной кириллицей.
7. `flutter analyze` — 0 замечаний, `flutter test` — зелёный, `flutter build apk --release` проходит.
