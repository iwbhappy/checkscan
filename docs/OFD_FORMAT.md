# Реальный формат ОФД «Казахтелеком»

Исследование выполнено 7 октября 2026 года на QR из `TZ.md` и фотографии
`Чек.jpg`. Получен **реальный успешный JSON чека**, он сохранён без изменений
в `test/fixtures/ofd_responses/ticket.json`. Сетевые ответы не подменялись
данными из ТЗ. Этап исследования завершён; для поддержки новых вариантов
ответа нужны дополнительные реальные чеки.

При проверке на Android обнаружена неполная TLS-цепочка сервера. Её безопасное
дополнение, источники CA и успешный живой запрос описаны в [OFD_TLS.md](OFD_TLS.md).

## Источники и воспроизведение

- [Страница чека](https://consumer.oofd.kz/?i=1462733895&f=010102236118&s=2002.00&t=20261007T153259).
- [Публичный API этого чека](https://consumer.oofd.kz/api/consumer-proxy/api/tickets/get-by-url?f=010102236118&i=1462733895&s=2002.00&t=20261007T153259).
- [Публичный JS с вызовом API и отображением чека](https://consumer.oofd.kz/_next/static/chunks/820e52187fc72343.js).
- Тела ответов: `test/fixtures/ofd_responses/consumer.html`, `ticket.json`.
- HTTP-статусы и заголовки: соседние `*.headers.txt`; SHA-256, URL и происхождение:
  `test/fixtures/provenance.json`.
- Снимки публичного JavaScript: `test/fixtures/ofd_assets/`.
- Фотография: `test/fixtures/photos/small_2026_10_07.jpg` — точная копия исходной.
- `test/fixtures/qr_strings.txt`: исходная строка ТЗ с `&amp;`, затем строка,
  действительно декодированная из фотографии. Это **один чек**, а не два примера.

Dev-скрипт печатает и сохраняет QR **до** HTML-декодирования, скачивает HTML
и найденный JSON API, сохраняет сырые байты, заголовки, итоговый URL и SHA-256:

```powershell
python -X utf8 tool/research_ofd.py --output build/ofd-research
```

Скрипт использует стандартную библиотеку Python и реальную сеть; в CI его не
вызывают. На этой машине первый запрос в sandbox упёрся в недоступный прокси
`127.0.0.1:9`; повтор с разрешённым сетевым доступом прошёл. Это ограничение
среды, а не ошибка ОФД.

OpenCV `QRCodeDetector` декодировал исходное фото при кропе
`x=740..1150, y=1950..2340` (оригинал 1920×2560) и увеличении ×3. Полное фото
и нижняя треть с ×1/×2/×3 данным декодером не распознались. Эти координаты —
свидетельство исследования одного снимка, не универсальная логика приложения.

## QR и транспорт

```text
http://consumer.oofd.kz?i=1462733895&f=010102236118&s=2002.00&t=20261007T153259
```

| Параметр | Назначение | Правило |
| --- | --- | --- |
| `i` | Фискальный признак | Строка, не преобразовывать в double |
| `f` | РНМ кассы | Сохранять исходную строку, для сравнения убрать ведущие нули |
| `s` | Итог | Десятичная строка → целые тиыны |
| `t` | Время QR | `yyyyMMddTHHmmss`, без зоны; не добавлять два часа |

Сначала декодируются HTML entities (`&amp;` → `&`). HTTPS успешно работает:
первичный GET отвечает `307 Location: /ru?...`, следующий — `200 text/html`.
Оба ответа сохранены в `consumer.headers.txt` (Date: 13:02:31 GMT).
Переход остаётся на `consumer.oofd.kz`. HTTP-fallback для этого чека не понадобился.

При проверке домена допустимы `oofd.kz` и поддомены с границей `.oofd.kz`,
но не строковый suffix вроде `eviloofd.kz`. Фактический исследованный хост —
`consumer.oofd.kz`; другие поддомены этим исследованием не подтверждены.
URL с userinfo, произвольным портом и редиректом на другой хост следует отклонять.

## Next.js и API

HTML — Next.js/React-страница формы. Товаров в HTML и hydration state нет.
В JS `820e52187fc72343.js`, функция `t_`, обнаружен запрос:

```text
GET /api/consumer-proxy/api/tickets/get-by-url?f=...&i=...&s=...&t=...
Content-Type: application/json
```

Все четыре параметра передаются **без изменения**, включая время и ведущие
нули РНМ. Host берётся из origin страницы. Браузерный код использует
`credentials: "include"`; наш запрос без cookies успешно вернул 200.
Применены `User-Agent: Mozilla/5.0` и `Accept-Language: ru`.

В форме присутствует reCAPTCHA, однако нормальный QR-сценарий самой страницы
в `useEffect` автоматически вызывает API, когда заполнены `i/f/s/t`. Этот
вызов не содержит CAPTCHA-токена. Исследование повторило именно этот
публичный сценарий; CAPTCHA не решалась и не обходилась. Если API позднее
потребует пользовательского действия, ответ нельзя выдавать за чек.

Реальный API-ответ: **HTTP 200**, `Content-Type: application/json`,
`Date: Wed, 07 Oct 2026 13:03:43 GMT`. Скрипт не отправлял cookie, авторизацию
или ключ. Данные доступны прямым GET (вариант A раздела 6.2 ТЗ); WebView для
исследованного чека не требуется.

## Подтверждённая структура ответа

Root — JSON object, в нём `ticket` и отдельные реквизиты продавца/кассы.
Все перечисленные ниже пути действительно присутствуют в сохранённом JSON.

| JSON path | Пример | Модель |
| --- | --- | --- |
| `orgTitle` | `ПАВЛОДАРСКИЙ ФИЛИАЛ ... "СКИФ ТРЕЙД"` | `sellerName`, полное значение |
| `orgId` | `131141020408` | `sellerBin` |
| `retailPlaceAddress` | `обл. Павлодарская, г. Павлодар, ул. Ак. Сатпаева 47, офис А` | `storeAddress` |
| `kkmFnsId` | `010102236118` | `kkmRegNumber` |
| `kkmSerialNumber` | `502220466` | `kkmSerial` |
| `ticket.fiscalId` | `1462733895` | `fiscalSign` |
| `ticket.options.children[]` | `{name: "printedDocumentNumber", value: "308128"}` | `receiptNumber` |
| `ticket.transactionDate` | `2026-10-07T15:32:59.000` | Локальные компоненты времени |
| `ticket.totalSum` | `2002.00` | `totalMinor = 200200` |
| `totalDiscount` | `0` | `discountMinor = 0` |
| `taxes[]` | `{rate: 0.16000, name: "", sum: 276.14}` | `vatRate = 16`, `vatMinor = 27614` |
| `ticket.payments[]` | `{paymentType: "CARD", sum: 2002.00}` | `paymentType = card` |
| `measureUnits` | `{"796": "шт "}` | Код → единица, trim пробелы |

`ofdName` отсутствует в JSON: принадлежность провайдеру подтверждается
реальной страницей и печатным чеком. `currency` отсутствует: KZT — заданное
ТЗ значение по умолчанию. `foundDate` — время поиска, **не** время покупки.

Товар — `ticket.items[]`, в исследованном чеке `itemType = 1`:

```json
{
  "commodity": {
    "barcode": null,
    "quantity": 1.0,
    "price": 299.00,
    "measureUnitCode": "796",
    "ntin": "0200092089208",
    "name": "Mars шоколадты батончигі 50,5гр snickers - Бат.snickers 50,5 - MARS",
    "sum": 299.00,
    "taxes": [
      {"inTotalSum": true, "sum": 41.24,
       "layout": {"taxCode": 100, "rate": 0.16000, "taxName": ""}}
    ]
  },
  "itemType": 1,
  "discount": null,
  "markup": null,
  "modifiers": [],
  "options": {"children": [], "value": "", "name": "empty"}
}
```

Выше приведено точное содержимое значимых полей первого элемента; поля
`sectionCode`, `exciseStamp`, `physicalLabel`, `productId`, `listExciseStamp`,
`code` опущены в примере, но сохранены в сыром JSON. `name` хранится полностью
как `rawName`, русская часть выделяется отдельно. `barcode` у всех четырёх
позиций `null`: нельзя подставлять штрихкод с фотографии или `commodity.code`.
`ntin` задан отдельной строкой. Все количества 1.0; весовой чек пока не получен.

| Позиция (русская часть) | Цена/сумма, ₸ | NTIN | НДС, ₸ |
| --- | ---: | --- | ---: |
| Бат.snickers 50,5 | 299.00 | 0200092089208 | 41.24 |
| Молоко галиц.1л 2,5% | 435.00 | 0200021763506 | 60.00 |
| Творог 9% полуж 250г | 489.00 | 0200134355469 | 67.45 |
| Сметана 400гр 15% | 779.00 | 0200020937090 | 107.45 |

Сумма позиций точно равна 2002.00. Скидки повторно не вычитаются.
`ticket.discount`, скидки позиций — null, `ticket.taxes` — пустой список;
сводный НДС находится в **root.taxes**. Нельзя брать только `ticket.taxes`.
`requestPayload` и `payload` — Base64-строки, для указанной модели их
декодирование не требуется. Их схема не исследовалась.

## Время и отличия от бумажного чека

Ответ содержит `transactionDate = 2026-10-07T15:32:59.000`, без `Z` и смещения.
JS портала показывает его через `new Date(transactionDate)` и
`format(date, "dd.MM.yyyy, HH:mm")`, то есть **07.10.2026, 15:32**. Код не
добавляет 2 часа. HTML содержит `timeZone: "Asia/Aqtau"` у провайдера
локализации, но это не отдельное поле зоны транзакции и не доказательство
часового пояса кассы. Сам QR и ответ совпадают до секунд.

Поэтому время ответа имеет приоритет, а не 17:32 с бумаги. Для хранения
используется указанное в ТЗ default-смещение UTC+5: `dateTimeUtc =
2026-10-07T10:32:59Z`, `tzOffsetMin = 300`. Это **явное допущение для
offset-less ответа**, а не установленная семантика внутренней БД ОФД.
Источник не позволяет доказать причину двухчасовой разницы; она остаётся
известным ограничением. Дедупликация от времени не зависит.

| Поле | Фото / пример ТЗ | Фактический ответ ОФД |
| --- | --- | --- |
| Время | 17:32 | 15:32:59, без зоны |
| НДС | 276.12 | 276.14 (совпадает с суммой четырёх налогов) |
| Скидки | 242.00 | totalDiscount = 0, других скидок нет |
| РНМ | 0010102236118 | 010102236118 |
| Продавец | ТОО «Скиф Трейд» | Полное наименование Павлодарского филиала |

В тестах проверяются **реальные** значения JSON. Нельзя заставлять parser
test ожидать 276.12 / 242.00 / 17:32: это означало бы незаметно выдумывать
поля или править реальный ответ. Фотография сохранена для документирования
этого расхождения; OCR не входит в v1.

## Границы подтверждённого

Один реальный чек подтверждает успешную продажу с CARD, четырьмя штучными
товарами, одной ставкой НДС, без переданных скидок. JSON успешного возврата,
весового товара, смешанной оплаты, нескольких ставок, 404 и 5xx не получен;
такие реальные фикстуры не выдаются за существующие. Коды `operationType`
и `itemType`, не встреченные в этом ответе, требуют дополнительных примеров.
В публичном JS есть ветки для скидок/наценок, но это само по себе не реальный
ответ соответствующего чека. Неизвестный товарный вариант следует сохранять
для проверки или выдавать типизированную ошибку, не молча терять позиции.

`consumer.expected.json` описывает реальную HTML-форму как ответ без чека;
`ticket.expected.json` — ожидаемую нормализованную модель успешного JSON.
Соседние expected-файлы созданы вручную **на основании** сырого ответа и
описанных правил, а не скачаны с сервера.
