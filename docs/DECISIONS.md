# Решения CheckScan

## Исходные данные и этапы

- Проект создан с нуля в корне `C:\PROJECTS\checkscan`, Flutter stable 3.44.8 / Dart 3.12.2. Версии разрешённых зависимостей закреплены `pubspec.lock`.
- Этапы 1–2: каркас Material 3 / Riverpod / GoRouter / ARB, Drift schema v1, реальное исследование ОФД и парсер. Проверка: `flutter analyze --no-pub` без замечаний, `flutter test --no-pub` — 39 тестов.
- Реальный HTTP-ответ имеет приоритет над описанием бумажного чека. Фактический НДС 276,14 ₸, скидка 0, дата-время 07.10.2026 15:32:59. Подробные расхождения и происхождение фикстуры — в `OFD_FORMAT.md`.
- Сеть требуется только для загрузки чека из ОФД. Аккаунтов, сервера, аналитики и OCR нет.

## Деньги, время, идентичность

- Суммы — целые тиыны; десятичные строки разбираются без умножения `double` на 100. Скидка из ответа справочная, повторно из итога не вычитается.
- `dedupKey = fiscalSign|normalizedKKM|qrTotalMinor` неизменяем после получения ОФД и ручных правок. Время не входит в ключ.
- До ответа ОФД часовой пояс QR неизвестен. `tzOffsetMin=null`, дата содержит компоненты QR в UTC-shaped значении; отображение не переводит их в системный пояс. Исходная ссылка сохраняется.
- Ответ ОФД содержит время без зоны. Применяем требуемый ТЗ default UTC+5; подтверждения зоны со стороны API нет. Двухчасовой сдвиг к бумажному чеку не прибавляем.
- Drift возвращает `DateTime` в зоне устройства; отображение всегда начинает с `.toUtc()`, затем добавляет сохранённое смещение.
- Чеки с расхождением позиций сохраняются с `needsReview`, без потери исходных сумм. Неподтверждённый формат возврата не считается обычной покупкой.

## Сеть и платформы

- API найден в публичном клиентском JavaScript ОФД. CAPTCHA ручной формы не обходится: QR-переход вызывает API автоматически.
- HTTPS по умолчанию. HTTP fallback разрешён только для `consumer.oofd.kz` при транспортной ошибке. Редиректы проверяются вручную и ограничены исходным хостом, число переходов ограничено.
- Сервер ОФД передаёт неполную TLS-цепочку. Для точного origin `https://consumer.oofd.kz:443` добавлен проверенный публичный промежуточный CA без отключения проверки HTTPS и без дополнительных сетевых обращений. Происхождение, ограничение срока действия и успешная проверка на Android: [OFD_TLS.md](OFD_TLS.md). TLS-ошибки выделены в отдельный `TlsFailure` с сохранением черновика и возможностью повтора.
- Android minSdk 24; только CAMERA и INTERNET. Системный выбор фото не требует доступа ко всей медиатеке. Cleartext разрешён ровно одному хосту через network security config; в iOS — точечное ATS-исключение.
- Сборка iOS требует macOS/Xcode; на Windows можно проверить Dart-код и конфигурацию, но нельзя подтвердить нативную сборку iOS.
- Release APK для локального тестирования использует debug signing, публикация в сторах вне ТЗ.
- Встроены два тестовых ассета (фото и реальный ответ) для device integration smoke; приложение их не загружает в пользовательскую историю.

## Проверки и границы

- В unit/widget/DAO тестах сеть заменена адаптером; реальные запросы выполняет только явный `tool/research_ofd.py`.
- Схема версии 1 тестируется на новой БД, FK, индексах, транзакциях и повторном открытии файла. Миграции из ещё не существующих версий не имитируются.
- Из `sqlite3_flutter_libs` актуальная версия помечена upstream как EOL: SQLite поставляется через native assets `sqlite3`; пакет оставлен для соответствия стеку ТЗ.

## Нативная конфигурация и диагностика SDK

- Зафиксирован `permission_handler 12.0.1`: версия 13 требовала Android SDK 37 с несовместимым в этой среде идентификатором платформы. Android собирается с SDK 36.
- ML Kit использует локальную встроенную модель штрихкодов. В manifest удалены DataTransport BackendDiscovery, JobInfoSchedulerService и AlarmManagerSchedulerBroadcastReceiver вместе с ACCESS_NETWORK_STATE. Проверен путь DefaultScheduler установленного transport-runtime 2.2.6: отсутствие backend отбрасывает диагностические события до сохранения/отправки. Это настройка компонентов закреплённой версии, а не официальный флаг ML Kit. При обновлении зависимостей необходимо повторить native smoke и `tool/check_android_manifest.py`.
- Автоматическая облачная копия Android отключена (`allowBackup=false`); пользователь самостоятельно сохраняет JSON/CSV. При полной очистке удаляются также временные файлы экспорта и debug-снимок QR в памяти; внешние копии, которые пользователь уже отправил/сохранил, не удаляются.
- iOS min 14 из-за file_picker_darwin. CocoaPods выбран явно (SwiftPM выключен локально в pubspec), permission_handler компилируется только с PERMISSION_CAMERA. Собираемость iOS на macOS остаётся непроверенной.

## Локальное сохранение и повторы, этапы 3–4

- Сначала в короткой транзакции сохраняется `pending` с известными полями QR, затем выполняется запрос ОФД. Сеть не удерживает транзакцию. Одновременные сканы защищены уникальным `dedupKey`; повторные запросы одного чека объединяются.
- Повторы после неудачной загрузки назначаются через 1, 5, затем 30 минут; последующие неудачи также откладываются на 30 минут. Пока приложение активно, таймер раз в 15 секунд проверяет срок. При запуске/возврате в приложение очередь перепроверяется сразу; обновление истории запускает принудительный повтор.
- Отдельного наблюдения за сетью и Android background service нет: после восстановления связи в открытом приложении сработает ближайший назначенный повтор, а не гарантированный мгновенный сетевой callback. После `stop` следующие элементы очереди не запускаются. Уже отправленный запрос может завершиться и сохранить результат.
- Перед сохранением ответа и ошибки повторно проверяется существование чека, `edited` и `status=ok`. Удаление во время запроса не отменяется поздним ответом; успешные или вручную изменённые данные не перезаписываются.
- Ручное редактирование доступно после успешной загрузки. Для `pending`/`error` остаются повтор, просмотр ссылки и удаление: пустой список ещё не загруженных позиций не превращает известный итог QR в ноль.
- Сохранение правок пересчитывает итог из сумм позиций, ставит `edited`, сохраняет исходный ключ QR. Сложение выполняется через `BigInt` с проверкой границ SQLite INTEGER. Когда итог изменён, прежние НДС и скидка очищаются, чтобы не показывать их как пересчитанные значения.
- Переименование магазина создаёт отдельную запись без БИН с прежним адресом, чтобы не менять остальные чеки этого продавца. Исходная запись магазина и ссылка ОФД сохраняются. Это следствие заданного ограничения `stores.bin UNIQUE`.
- Undo восстанавливает чек и позиции транзакционно, по возможности с исходными идентификаторами. Если тот же QR уже добавлен заново, возвращается существующий чек без перезаписи. Удалённая пользовательская категория заменяется «Прочее».

## История, категории и статистика, этапы 4–6

- Границы фильтров — локальные календарные компоненты; начало включительно, конец исключительно. Их нельзя заранее переводить из UTC+5 в UTC. SQL сравнивает `dateTimeUtc + COALESCE(tzOffsetMin, 0)` с такими же календарными компонентами. Поэтому подтверждённые даты и QR с неизвестной зоной попадают в день, который виден пользователю. История сортируется по этому же отображаемому времени.
- SQL отбирает период, магазин, категорию и суммы. Поиск магазина/позиций выполняется через Unicode lowercase в Dart, поскольку SQLite `LOWER`/`NOCASE` без ICU не приводят кириллицу. FTS5 в v1 не используется; при очень большой истории этот поиск потребует отдельной оптимизации.
- Стартовые ключевые слова находятся в `assets/category_rules.json` и загружаются идемпотентно. Приоритет: пользовательские правила, затем встроенные, затем «Прочее». Внутри уровня штрихкод точнее полного нормализованного имени, затем ключевого слова; более длинное слово проверяется первым.
- Запомненное полное имя использует `kind=keyword`, `pattern="=нормализованное имя"`: знак `=` — внутренний маркер точного совпадения, позволяющий сохранить два вида правил исходной схемы. Нормализация приводит регистр, пробелы и `ё` к `е`.
- Категория нового чека выбирается по наибольшей абсолютной сумме позиций. Удаление пользовательской категории переводит её чеки и позиции в «Прочее» и удаляет связанные правила. Встроенные категории удалить нельзя.
- В статистику входят известные суммы всех сохранённых чеков, включая `pending` и `error`. Позиции распределяются по своим категориям, а разница `итог чека − сумма позиций` — по категории чека. Это сохраняет точное равенство итога истории, категорий и графика, включая чеки с `needsReview`; справочная скидка повторно не вычитается. При завышенной сумме позиций распределение может иметь отрицательную корректировку.
- Топ товаров по частоте считает разные чеки, а не число одинаковых строк в одном чеке. Товары объединяются по штрихкоду, при его отсутствии — по сохранённому имени. Возвращаются первые 10 магазинов/товаров.
- Полный календарный месяц сравнивается с полным предыдущим месяцем, год — с предыдущим годом; остальные интервалы — с непосредственно предшествующим интервалом той же длительности. При нулевой сумме прошлого периода процент изменения не определяется.

## Резервные копии и очистка, этап 7

- JSON имеет `format=checkscan`, `version=1`, UTC-даты ISO 8601 и полные локальные таблицы. `debugRaw` в JSON/CSV не экспортируется. Импорт не выполняет сетевых запросов.
- Перед записью проверяются типы, диапазоны, даты, идентификаторы, ссылки между таблицами и соответствие `dedupKey` исходному QR. Неизвестная версия отличается от повреждённого файла. Запись выполняется одной транзакцией; идентификаторы переназначаются, существующие чеки с таким же QR не заменяются.
- Встроенные категории сопоставляются по стабильным ID, пользовательские — по имени/цвету/иконке; магазины — по БИН либо имени/адресу. При конфликте пользовательского правила остаётся локальное правило. Представление встроенных категорий восстанавливается из копии.
- Системный выбор файла в настройках ограничивает размер 20 МиБ до чтения; сам парсер JSON дополнительно ограничивает строку 32 × 1024 × 1024 кодовыми единицами UTF-16, каждый список — 100 000 строками, текстовое поле — 100 000 кодовыми единицами. Резервные копии существенно большего размера потребуют потокового формата в следующей версии.
- CSV создаётся двумя файлами: чеки и позиции. Кодировка UTF-8 с BOM, разделитель `;`, десятичная запятая, кавычки и переносы экранируются библиотекой CSV. Текст, начинающийся с формульного префикса Excel, получает защитный апостроф; числовые суммы остаются числами.
- «Удалить все данные» требует двух подтверждений, удаляет чеки, позиции, магазины, пользовательские категории и правила, затем восстанавливает встроенный словарь правил. 16 встроенных категорий и настройки внешнего вида остаются. Последовательности SQLite не сбрасываются, поэтому поздний запрос старого чека не совпадёт с ID вновь импортированного чека.

## Ручной ввод

- Покупки без QR (чужой формат QR, нечитаемый чек) вводятся вручную через тот же редактор (`/receipts/new`). Такой чек сразу `status=ok`, `edited=true`, `sourceUrl=''`, `dedupKey='manual:<микросекунды>-<случайное>'` — дубликаты по QR для него не определяются. Признак — `ReceiptRow.isManual`.
- Магазин ручного чека ищется по точному имени без БИН и адреса, иначе создаётся. Категория чека — доминирующая категория позиций, если не выбрана явно. Категория новой позиции подсказывается по правилам, пока пользователь не выбрал её сам; «Запомнить» предлагается только при явном выборе.
- JSON-импорт принимает ручные чеки только с пустым `sourceUrl` и `status=ok`.
